# Отчёт по приложению Tbonk Tasks

> Начиная с `hw_2`, Python-код, зависимости и тесты находятся в `backend/`; команды ниже учитывают эту структуру. В самой ветке `hw_1` они остаются в корне.

## Доменная область

Tbonk Tasks — небольшой трекер задач. Пользователь создаёт задачи, описывает их, переводит между статусами «к выполнению», «в работе» и «готово», редактирует и удаляет. Приложение намеренно сделано компактным, чтобы его было удобно развивать в следующих домашних заданиях: добавлять авторизацию, балансировку, миграции и новые доменные сущности.

## Стек реализации

- Python 3.12;
- Flask 3 — HTTP/REST API и раздача статических файлов;
- psycopg 3 — подключение к PostgreSQL;
- PostgreSQL 16;
- HTML, CSS и vanilla JavaScript — фронтенд без сборщика;
- Docker и Docker Compose — воспроизводимый запуск;
- Gunicorn — production WSGI-сервер.
- pytest и GitHub Actions — автоматические интеграционные тесты и CI.

Запуск:

```bash
cp .env.example .env
docker compose up --build
```

После запуска приложение доступно на <http://localhost:8000>, проверка состояния — на `/health`.

CI запускается на push в master/main и на pull request. В workflow поднимается настоящий PostgreSQL 16 как service container, после чего выполняются проверки синтаксиса и интеграционные тесты CRUD/валидации через Flask test client.

## Основные сущности

### Task (задача)

Поля: `id`, `title`, `description`, `status`, `created_at`, `updated_at`. Статус ограничен значениями `todo`, `in_progress`, `done`. Сейчас приложение использует одну сущность, потому что полного CRUD над ней достаточно для предметной области и последующего расширения.

## REST API и CRUD

- `GET /api/tasks` — список задач; поддерживает фильтр `?status=done`;
- `GET /api/tasks/{id}` — одна задача;
- `POST /api/tasks` — создание;
- `PUT /api/tasks/{id}` — полное обновление;
- `DELETE /api/tasks/{id}` — удаление;
- `GET /health` — проверка доступности приложения и базы данных.

## Соответствие 12 факторам

### I. Codebase (Одна кодовая база — одно приложение)

Весь исходный код находится в одном Git-репозитории. Один репозиторий можно развернуть как несколько одинаковых экземпляров сервиса, поэтому нет отдельных вручную поддерживаемых копий кода.

### II. Dependencies (Зависимости)

Все внешние зависимости явно перечислены в `backend/requirements.txt` с зафиксированными версиями. Они устанавливаются автоматически во время сборки Docker-образа, системные пакеты на машине разработчика не требуются.

### III. Config (Конфигурация)

Изменяемые параметры читаются из окружения. Compose подставляет `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` из `.env` в контейнер PostgreSQL и передаёт приложению соответствующие `PGDATABASE`, `PGUSER`, `PGPASSWORD` вместе с `PGHOST=db`. Приложение также поддерживает `DATABASE_URL` для запуска вне Compose. Gunicorn читает `PORT` и `WEB_CONCURRENCY` в `backend/gunicorn.conf.py`. `HOST_PORT` управляет внешним портом Compose. `.env.example` содержит только учебный пример; `.env` исключён из Git и контекста Docker.

### IV. Backing services (Внешние сервисы)

PostgreSQL — подключаемый внешний ресурс. Его адрес задаётся `PGHOST`/`PGPORT` или `DATABASE_URL`: локально можно использовать один контейнер, а в другом окружении — управляемую базу без изменения исходного кода.

### V. Build, release, run (Сборка, релиз, запуск)

Этапы разделены: `Dockerfile` собирает неизменяемый образ с зависимостями, `docker compose` задаёт релиз (образ плюс конфигурация), а Gunicorn запускает приложение. Повторный запуск использует тот же образ.

### VI. Processes (Процессы)

Веб-приложение работает как stateless-процесс Gunicorn. Состояние не хранится в памяти процесса: данные находятся в PostgreSQL, поэтому экземпляры можно масштабировать горизонтально.

### VII. Port binding (Привязка к портам)

Gunicorn поднимает HTTP-сервер на порту из `PORT` (по умолчанию `8000`). Он публикуется Docker Compose наружу, а не предполагает наличие общего веб-сервера на хосте.

### VIII. Concurrency (Параллелизм)

Масштабирование достигается количеством Gunicorn workers и реплик контейнера. Долгоживущего локального состояния нет, поэтому запросы можно распределять между процессами.

### IX. Disposability (Одноразовость процессов)

Контейнер можно быстро остановить и запустить заново. PostgreSQL имеет healthcheck, а приложение не хранит пользовательское состояние в памяти. Корректное завершение и короткий старт позволяют безопасно перезапускать web-процесс.

### X. Dev/prod parity (Паритет разработки и production)

И разработка, и запуск выполняются через тот же Docker Compose с PostgreSQL 16 и тем же образом Python-приложения. Это уменьшает различия между окружениями.

### XI. Logs (Логи)

Приложение и Gunicorn пишут логи в stdout/stderr контейнера. Docker может собирать их стандартными средствами; приложение не создаёт локальные файлы логов.

### XII. Admin processes (Административные процессы)

Схема создаётся отдельной командой `python -m backend.manage init-db`. В Compose это одноразовый сервис `init-db`: он использует тот же образ и настройки БД, ожидает готовности PostgreSQL и завершается. Сервис `web` запускается после успешного завершения `init-db`. Импорт `backend/wsgi.py` и запуск `backend/app.py` больше не создают таблиц. Повторный ручной запуск: `docker compose run --rm init-db`. Команда идемпотентна для первоначального создания схемы, но не заменяет миграции существующих таблиц.

## Ограничения и развитие

В учебной версии нет аутентификации и версионирования схемы. Таблица создаётся отдельной административной командой; изменение уже существующей схемы потребует миграций. Автоматические тесты API и GitHub Actions уже реализованы, включая проверку длины названия при POST/PUT и отсутствие обращения к БД при импорте WSGI. Следующие шаги для production: Alembic, пользователи, управление секретами, резервные копии и наблюдаемость. Одноузловой PostgreSQL пока остаётся единой точкой отказа.
