# ДЗ‑2: от Compose к Kubernetes

## Зачем ещё один способ запуска

В ДЗ‑1 мы описали несколько контейнеров на одной машине. Kubernetes добавляет контроллеры: они постоянно сравнивают желаемое состояние с фактическим и исправляют расхождения. Если задано две веб-реплики и одна умерла, контроллер создаст новую. `kubectl apply` передаёт описание желаемого состояния API-серверу, а не запускает процесс напрямую.

minikube поднимает учебный Kubernetes. На Mac контейнеры Linux живут в виртуальной машине: ядро macOS не умеет исполнять Linux-контейнеры самостоятельно. Это объясняет, почему одного скачанного `docker` недостаточно и почему образ на ноутбуке не обязательно виден внутри minikube.

## Pod, Deployment, ReplicaSet

Pod — минимальная единица размещения. В нём один или несколько контейнеров с общей сетью: контейнеры одного пода видят друг друга через localhost. У веб-приложения в этой домашке один контейнер на под. Deployment управляет ReplicaSet, а тот поддерживает число подов. Руками создавать два одинаковых пода не нужно.

`replicas: 2` — количество подов; `WEB_CONCURRENCY=2` — количество Gunicorn workers внутри каждого пода. Это разные уровни параллелизма. Здесь четыре рабочих Python-процесса на две веб-реплики. Ресурсные requests помогают планировщику разместить под; limits ограничивают потребление.

При `kubectl scale ... --replicas=3` меняется состояние кластера. Следующий `apply` файла с `replicas: 2` вернёт декларативное значение. Для постоянного изменения надо менять YAML и фиксировать его Git-коммитом.

## Зачем нужен Service

IP пода меняется при пересоздании. Приложению нельзя прописывать временный IP БД. Service задаёт постоянное DNS-имя и выбирает поды по labels. У веба selector `app: tbonk` должен совпадать с labels шаблона пода. Иначе Service существует, но не имеет адресатов.

PostgreSQL получает headless Service, возвращающий IP его пода. Для одной БД это достаточно; StatefulSet использует тот же Service для стабильной сетевой идентичности. `postgres` внутри namespace tbonk разворачивается через DNS в адрес БД. Из другого namespace нужен `postgres.tbonk.svc.cluster.local`.

`ClusterIP` не открывает порт наружу. Для учебной демонстрации используем `kubectl port-forward`, который нужно держать работающим. На ноутбуке это удобнее, чем разбирать ingress, DNS и TLS раньше времени.

## Почему данные не должны жить только в контейнере

Файловая система контейнера временная. PersistentVolumeClaim запрашивает постоянное место, а storage provisioner minikube создаёт volume. StatefulSet закрепляет claim за ordinal `postgres-0`. Перезапуск пода и удаление всего кластера — разные операции: удаление minikube может уничтожить его локальные диски. PVC не является резервной копией.

## ConfigMap, Secret и Job

ConfigMap содержит несекретные настройки. Secret содержит пароль и подставляется в окружение. В Kubernetes Secret обычно кодируется base64 при чтении JSON/YAML; base64 не шифрование. В репозитории оставлен явно учебный пароль, чтобы пример запускался. Реальные секреты должны доставляться другим способом.

Job запускает отдельную команду и считается успешной после выхода с кодом 0. В отличие от Deployment, задача Job не поддерживать бесконечно живущий HTTP-сервер. Скрипт развёртывания ждёт PostgreSQL, запускает Job и проверяет её завершение. При следующем деплое Job пересоздаётся, потому что Kubernetes не разрешает менять её pod template. Сама команда создания схемы допускает повторное выполнение.

## Три проверки состояния

Startup probe — процесс вообще успел запуститься? Пока она не проходит, остальные проверки не мешают запуску. Liveness — процесс способен отвечать? Неудача приводит к перезапуску контейнера. Readiness — можно ли сейчас направлять ему пользовательские запросы? Неудача убирает под из endpoints Service, но не убивает его.

Если БД упала, перезапуск каждой веб-реплики редко помогает. Поэтому liveness не проверяет БД, а readiness проверяет. Дальше для пользовательской доступности понадобится отдельный пробер: Kubernetes readiness сама по себе не измеряет качество пользовательского сценария.

## Как диагностировать ошибки

- `ImagePullBackOff`/`ErrImageNeverPull`: проверить тег, загрузку в нужный профиль и imagePullPolicy.
- `Pending`: смотреть `kubectl describe pod`, requests, свободную память и PVC.
- `CrashLoopBackOff`: читать `kubectl logs pod --previous` и описание пода.
- `Running`, но `0/1 Ready`: читать readiness и состояние БД/таблицы.
- Service не отвечает: проверить labels, endpoints и порт контейнера.
- Job не завершилась: `kubectl logs job/tbonk-init-db`; отдельно проверить доступность PostgreSQL.

К каждой команде добавляй `--context tbonk-homework` и `-n tbonk`, чтобы не попасть в другой кластер или namespace. Скрипт делает это явно.

## Что сравнивать в Git

```bash
git diff hw_1...hw_2
```

Основной diff — манифесты, скрипт развёртывания и проверки состояния. Приложение по-прежнему делает тот же CRUD: Kubernetes меняет его эксплуатацию, а не предметную область.
