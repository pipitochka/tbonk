# ДЗ‑6: от плохого графика до полезного уведомления

## Условие не равно сообщению

VictoriaMetrics хранит числа. vmalert периодически вычисляет выражение. Если результат содержит серию, условие активно для её набора labels. Alertmanager принимает активные алерты, группирует их, учитывает маршруты и отправляет webhook. Inbox показывает полученное сообщение. Это четыре отдельных шага, поэтому «график плохой» не гарантирует доставку.

У алерта есть состояния inactive, pending и firing. `for: 1m` требует, чтобы условие сохранялось в последовательных вычислениях целую минуту. Если оно перестало выполняться, ожидание сбрасывается. Эта выдержка не совпадает с окном `[2m]`: окно определяет, какие samples попадают в rate, а for — как долго уже посчитанное условие должно оставаться истинным.

## Как выбирать сигнал

Сервисный алерт отвечает на вопрос «страдают ли пользователи?». Ошибки и медленные успешные операции напрямую связаны с работой с задачами. Runtime-алерт отвечает «какой ресурс может стать причиной?». CPU и память помогают диагностировать ситуацию, но могут быть высокими без нарушения пользовательской цели.

Порог должен быть объясним: 100 MiB RSS — запас до лимита 256 MiB для этого маленького приложения; 0.8 CPU — приближение к ограничению в одно ядро. На другом приложении эти числа надо пересмотреть. «80% CPU» здесь значит 0.8 процессорной секунды в секунду, а не 80% всех восьми ядер ноутбука.

## Labels определяют отдельные алерты

У ошибки, посчитанной суммой по всем подам, один общий алерт сервиса. У process-метрики остаётся label pod, поэтому отдельный worker с высокой памятью даёт отдельный экземпляр алерта. Alertmanager может объединить несколько таких экземпляров в одно уведомление по alertname/service/severity.

Нельзя помещать меняющееся текущее значение в label: каждый новый набор labels станет новым алертом и заново начнёт for. Динамические значения обычно размещаются в annotations. В нашем учебном конфиге annotations содержат стабильное объяснение и действие для диагностики.

## Зачем group_wait, repeat_interval и resolved

Первое короткое ожидание позволяет собрать несколько похожих событий в одно сообщение. group_interval ограничивает частоту обновлений группы. repeat_interval определяет напоминания о проблеме, которая не исчезла. `send_resolved` завершает историю уведомлением о восстановлении.

Resolved не приходит мгновенно после off: плохие измерения ещё находятся в `[2m]`, затем нужно очередное вычисление и доставка. Это ожидаемая задержка системы, а не обязательно баг.

## Почему выбран локальный webhook

В задании важно доказать, что сообщение реально прошло из Alertmanager к получателю. Для этого не обязательно подключать личный Telegram-бот или корпоративную почту. Локальный inbox принимает тот же webhook payload и показывает статус, название, время и описание. Он не рисует состояние напрямую по правилам — сообщение должно действительно прийти HTTP-запросом.

Это учебный получатель. Его память ограничена 100 сообщениями, нет авторизации и постоянного хранения, а Service доступен только внутри кластера/через административный port-forward. Для реальной дежурной службы нужен надёжный канал вне того же кластера, иначе отказ всего кластера выключит и уведомления.

## Как доказать правильность

Есть три разных уровня проверки. Парсер проверяет синтаксис YAML и выражений. Unit-тест правил подставляет искусственные временные ряды и проверяет пороги/выдержки. Сквозной эксперимент меняет реальное приложение, ждёт реальные метрики и подтверждает настоящее уведомление. Ни один уровень полностью не заменяет другие.

В unit-тесте нулевой трафик не должен вызвать процентный алерт. Высокая ошибка в первые 45 секунд не должна быть firing из-за for. Устойчивые ошибки через три минуты — должны. Метрики памяти и CPU проверяются отдельно. В сквозной проверке дополнительно могут выявиться проблемы DNS, scrape labels, маршрутизации и доступности receiver.

## Почему нужен алерт на сам мониторинг

Если пробер вчера последний раз записал success=1 и завис, один Gauge будет выглядеть хорошо. Timestamp последнего завершения выявляет зависание, up — недоступность HTTP-экспортера, absent — исчезновение ряда после удаления pod. Это разные классы отказа.

Всё равно остаётся внешний предел: если сломалась сама VictoriaMetrics или весь кластер, внутренний vmalert может не доставить сообщение. Полноценный monitoring-of-monitoring располагают вне общей точки отказа. В этой домашке однодовый minikube намеренно остаётся учебным стендом.

## Как работать с ветками после завершения

Для каждой домашки используется одна ветка: `hw_1`–`hw_6`. Все доработки и исправления коммитятся и отправляются прямо в ветку соответствующей домашки. В `hw_1` уже включены исправления замечаний. Домашки образуют последовательную цепочку; для просмотра изменений сравнивайте текущую ветку с предыдущей. Новые коммиты в предыдущей домашке не появляются в следующих автоматически: при необходимости их переносят отдельно.

```bash
# Реализация шестой домашки относительно предыдущей:
git diff hw_5...hw_6
# Последующие исправления шестой домашки:
git switch hw_6
# После внесения изменений и проверок:
git add <изменённые-файлы>
git commit -m "Fix homework 6"
git push origin hw_6
```

Для PR первой домашки базой служит `master`, для следующих — предыдущая домашка. Отдельные ветки для исправлений не создаются.
