# ДЗ‑4. Метрики приложения, Python и PostgreSQL

## Стек

`prometheus-client==0.21.1` внутри Python-приложения, `postgres-exporter:v0.17.1` рядом с PostgreSQL, официальный Helm-chart `victoria-metrics-single` версии `0.29.0` (VictoriaMetrics `v1.134.0`). Конфигурация находится в `k8s/metrics/values.yaml`.

Single-node VictoriaMetrics сам выполняет scrape и Kubernetes service discovery. Отдельный vmagent здесь не нужен: задание требует сбор через discovery, но не обязательно отдельный процесс vmagent. Статус целей доступен на `/targets` самого VictoriaMetrics, а не на порту 8429. Сервис с фиксированным именем `vm-single`, порт 8428, namespace `monitoring`, PVC 2 GiB и retention 7 дней.

## Экспорт Python и Flask

`backend/metrics.py` регистрирует стандартные `GCCollector`, `PlatformCollector` и `ProcessCollector`. На Linux доступны `process_resident_memory_bytes`, `process_cpu_seconds_total`, `process_open_fds`, метрики Python GC и `python_info`. Метрики процесса зависят от платформы: на macOS часть process-коллектора отсутствует; целевой runtime контейнеров — Linux.

`post_worker_init` Gunicorn запускает HTTP-сервер метрик на отдельном порту 9100. Путь — `/metrics`, авторизация не требуется. В пользовательском Service публикуется только порт 8000; в Compose порт метрик тоже не публикуется. `/metrics` на пользовательском HTTP-порту возвращает 404. Доступ к 9100 имеют внутренние клиенты кластера; административный port-forward возможен. Изоляция от других недоверенных подов потребовала бы NetworkPolicy с поддерживающим CNI — такой защиты здесь не заявляется.

Клиент поддерживает Prometheus text и OpenMetrics по HTTP content negotiation. Для явной проверки OpenMetrics отправить `Accept: application/openmetrics-text`; ответ должен содержать `# EOF`.

Используется один worker с четырьмя потоками на под; значение `WEB_CONCURRENCY`, отличное от 1, приводит к понятной ошибке конфигурации. Это предотвращает экспорт случайной доли счётчиков из одного из нескольких процессов. Горизонтальное масштабирование выполняется через Deployment. Пользовательские данные по-прежнему находятся в БД; счётчики процесса сбрасываются при рестарте.

## Бизнес-метрики

| Метрика | Тип | Когда изменяется |
|---|---|---|
| `tbonk_tasks_created_total` | Counter | Успешно закоммичена новая задача |
| `tbonk_tasks_updated_total` | Counter | Успешно закоммичено обновление существующей задачи |
| `tbonk_tasks_deleted_total` | Counter | Успешно удалена существующая задача |
| `tbonk_tasks_completed_total` | Counter | Задача впервые/повторно вошла в done из другого статуса или сразу создана как done |
| `tbonk_task_operations_total{operation,outcome}` | Counter | Завершён API-вызов list/read/create/update/delete, с исходом success/client_error/server_error |
| `tbonk_task_operation_duration_seconds{operation,outcome}` | Histogram | Длительность того же вызова; buckets включают 0.5 секунды для будущего SLO |

Четыре первые метрики — доменные события, а не число HTTP-запросов. Повторное PUT с `status=done` увеличит updated, но не completed. Если задачу вернуть в todo и снова завершить, completed увеличится ещё раз. Это число завершений, не число уникальных задач.

Инкременты выполняются после выхода из транзакции. Для завершения при update предыдущий статус читается с `FOR UPDATE`, поэтому два конкурентных обновления не считают один переход дважды. 400, 404, 503 и rollback не считаются успешной доменной операцией. Между коммитом и инкрементом всё ещё возможен crash: эти счётчики предназначены для мониторинга, не для финансовой отчётности и аудита exactly-once.

Дополнительно `tbonk_http_requests_total{method,route,status_class}` измеряет HTTP-фреймворк. Probes `/live` и `/health` исключены. В labels нет title/task_id/request_id: кардинальность ограничена типами операций и шаблонами маршрутов.

## PostgreSQL exporter

Экспортер — второй контейнер в pod `postgres-0`, слушает 9187 и подключается к `localhost:5432`. Контейнеры одного пода разделяют сеть; отдельный Service БД для этого соединения не нужен. Логин приходит из ConfigMap, пароль — из Secret. Проверяются `pg_up`, `pg_stat_database_xact_commit`, `pg_stat_database_numbackends` и другие стандартные показатели.

Для компактного учебного стенда используется тот же пользователь БД. В production нужен отдельный пользователь с `pg_monitor` и минимальными правами. Экспортер не обязан быть написан на Python: формат экспорта одинаков для разных языков.

## Service discovery

Аннотации находятся именно в `spec.template.metadata.annotations` Deployment/StatefulSet, чтобы оказаться на Pod. Наличие аннотаций само по себе не запускает сбор: конфигурация VictoriaMetrics должна читать их.

`role: pod` обнаруживает поды; relabel оставляет `prometheus.io/scrape=true`, Running и единственный контейнерный порт с именем `metrics`. Затем подставляет путь и порт из аннотаций и добавляет labels `app`, `namespace`, `pod`. Фильтр имени порта нужен, чтобы один под с HTTP и metrics не скрейпился дважды. Каждая веб-реплика — отдельный target: scrape через балансирующий веб-Service пропустил бы часть процессов.

## Запуск и проверка

Собрать и загрузить `tbonk-tasks:hw4` по ДЗ‑2, затем:

```bash
bash scripts/deploy-app.sh
bash scripts/deploy-metrics.sh
kubectl --context tbonk-homework -n monitoring get pods,svc
kubectl --context tbonk-homework -n monitoring port-forward svc/vm-single 8428:8428
```

В другом терминале:

```bash
curl 'http://localhost:8428/api/v1/label/__name__/values'
curl -G 'http://localhost:8428/api/v1/query' --data-urlencode 'query=up{job="kubernetes-pods"}'
curl -G 'http://localhost:8428/api/v1/query' --data-urlencode 'query=pg_up{app="postgres"}'
curl -G 'http://localhost:8428/api/v1/query' --data-urlencode 'query=process_resident_memory_bytes{app="tbonk"}'
curl -G 'http://localhost:8428/api/v1/query' --data-urlencode 'query=sum(tbonk_tasks_created_total{app="tbonk"})'
```

Открыть http://localhost:8428/targets и http://localhost:8428/vmui/. Подождать несколько scrape-интервалов. Создать, завершить и удалить задачу в UI, увидеть рост соответствующих счётчиков. Для графика скорости использовать `sum(rate(tbonk_tasks_created_total{app="tbonk"}[5m]))`, а не сумму абсолютных counters через перезапуски.

Сценарий скринкаста: показать поды → `/targets` с двумя веб-целями и PostgreSQL → runtime-метрику → `pg_up=1` → изменить задачи в UI → показать изменение четырёх бизнес-счётчиков. Фактические результаты проверки отделяются от сценария в `docs/Проверка.md`.
