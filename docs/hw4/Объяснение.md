# ДЗ‑4: как из действий получаются временные ряды

## Метрика — числовое измерение во времени

Одна серия — имя метрики плюс полный набор labels. Например `tbonk_task_operations_total{operation="create",outcome="success",pod="tbonk-abc"}` и такая же серия с другим pod — разные ряды. Каждые 15 секунд сборщик получает текущее число и сохраняет пару «время, значение».

VictoriaLogs хранит события; VictoriaMetrics — временные ряды. Похожие названия продуктов не означают одинаковые API или язык запросов. В логах используется LogsQL, в метриках — PromQL-совместимый MetricsQL. Оба продукта имеют vmui, но это разные интерфейсы на 9428 и 8428.

## Counter, Gauge, Histogram

Counter растёт и сбрасывается при рестарте процесса. Он подходит для числа созданий, ошибок, завершений. `rate(counter[5m])` оценивает среднюю скорость в секунду с учётом сбросов; `increase(counter[5m])` — прирост за окно. При нескольких подах сначала вычисляют rate каждого ряда и только потом суммируют. Иначе сброс одного процесса можно спутать с изменением суммарного счётчика.

Gauge может расти и падать: память процесса, число открытых соединений, температура. Для него обычный `rate` часто не имеет предметного смысла.

Histogram состоит из счётчиков buckets, count и sum. Bucket с `le="0.5"` считает наблюдения длительностью не более 0.5 секунды. Buckets накопительные: запрос за 0.1 секунды входит и в le=0.1, и в le=0.5, и в +Inf. Их нельзя складывать между собой как независимые корзины. Деление прироста bucket 0.5 на прирост count даёт долю быстрых запросов.

Средняя задержка — rate(sum)/rate(count), но она скрывает редкие медленные запросы. `histogram_quantile(0.95, sum by (le)(rate(..._bucket[5m])))` оценивает p95. Точность ограничена границами buckets. Для SLO «95% быстрее 500 мс» удобнее и прозрачнее доля bucket 0.5, чем приблизительный p95.

## Какие события считать успешными

Успех HTTP и успешное изменение БД связаны, но не идентичны. Счётчик созданий увеличивается после commit. Если считать до SQL, неудачные запросы будут выглядеть как созданные задачи. Если считать каждое присваивание done, повторный PUT станет ложным завершением. Поэтому обновление читает прежний статус с блокировкой строки внутри той же транзакции.

Операционные счётчики считают результат запроса и включают ошибки. Это нужно для отношения успешных операций ко всем допустимым попыткам. Только по `tasks_created_total` невозможно узнать долю ошибок: нужен знаменатель.

## Почему один worker

Обычный Python-клиент держит counters в памяти процесса. Два Gunicorn workers означают две независимые копии. Если `/metrics` случайно обслуживает один из них, график прыгает и теряет события. У библиотеки есть multiprocess mode, но он требует отдельного каталога и ограничивает process-коллекторы. Для этого небольшого проекта проще один worker с четырьмя потоками и несколько подов. Потоки делят память, библиотека синхронизирует свои счётчики.

Это осознанное ограничение конфигурации. Увеличить `WEB_CONCURRENCY` и надеяться на правильный сбор нельзя. Масштабирование подами оставляет каждому процессу собственный стабильный target.

## Pull и service discovery

Приложение только отдаёт измерения; оно не знает адрес VictoriaMetrics. Сборщик сам приходит на 9100. В этом преимущество pull: список целей, частоту и правила хранения можно менять централизованно.

Статический список IP плохо подходит для Kubernetes, где поды постоянно пересоздаются. Service discovery читает Kubernetes API. Аннотации — соглашение, по которому сборщик понимает, какие поды и порты ему интересны. Relabeling превращает Kubernetes-метаданные в адрес цели и полезные labels.

`up=1` означает, что HTTP-scrape цели удался. Это не доказывает работоспособность пользовательского CRUD: процесс может отдавать метрики при упавшей БД. Поэтому отдельно проверяем `pg_up`, а в ДЗ‑5 добавим пользовательский пробер.

## Почему не использовать task_id в label

Каждое уникальное значение создаёт новые серии, а Histogram умножает их ещё на число buckets. Если добавлять ID каждой задачи или запроса, TSDB будет хранить огромное число короткоживущих рядов. Для метрик нужны ограниченные категории: create/update/delete, success/error. Конкретный request_id уже есть в логах.

## Практическая диагностика

Порядок проверки: ответ `/metrics` внутри пода → цель обнаружена на `/targets` → scrape успешен → серия появилась в API → график выбран за правильный диапазон. Если серия отсутствует, это не всегда ноль: сборщик мог ещё не прийти, label-фильтр мог исключить цель, либо метрика на этой платформе вообще не существует.
