# ДЗ‑1: как устроен проект и зачем понадобились исправления

> Начиная с `hw_2`, Python-код, зависимости и тесты находятся в `backend/`; команды ниже учитывают эту структуру. В самой ветке `hw_1` они остаются в корне.

## 1. Как проходит действие пользователя

Допустим, ты нажимаешь «Новая задача», заполняешь название и нажимаешь «Сохранить».

1. `frontend/index.html` задаёт форму, `styles.css` — оформление, `app.js` — поведение кнопок.
2. Обработчик `form.onsubmit` в `app.js` собирает JSON и отправляет `POST /api/tasks` через `fetch`.
3. В контейнере порт слушает Gunicorn. Он принимает HTTP и вызывает Flask через стандарт WSGI. `backend/wsgi.py` лишь экспортирует объект `app`.
4. Flask выбирает функцию `create_task` по HTTP-методу и адресу.
5. Функция проверяет название и статус. При ошибке возвращает JSON и HTTP 400.
6. `psycopg` открывает соединение с PostgreSQL. SQL использует параметры `%s`: значения передаются отдельно от текста SQL, а не склеиваются в строку.
7. `INSERT ... RETURNING` сразу возвращает созданную строку. Контекст соединения коммитит транзакцию при нормальном выходе и откатывает при исключении.
8. `serialize_task` превращает строку в словарь, даты — в ISO-строки. Flask возвращает JSON и 201.
9. JavaScript закрывает форму, заново получает список и перерисовывает карточки.

Это клиент-серверное приложение: браузер не ходит в PostgreSQL напрямую. Пароль БД нужен серверу, а не JavaScript. Все экземпляры сервера работают с одной БД. Перезапуск приложения не должен удалять задачи.

## 2. Карта файлов

| Файл | Ответственность |
|---|---|
| `backend/app.py` | Flask, HTTP-маршруты, валидация и SQL |
| `backend/wsgi.py` | Точка импорта приложения для Gunicorn |
| `backend/gunicorn.conf.py` | Порт, число процессов и вывод логов Gunicorn |
| `backend/manage.py` | Одноразовые административные команды |
| `frontend/` | Интерфейс без отдельной сборки и Node.js |
| `backend/requirements.txt` | Зафиксированные зависимости Python |
| `Dockerfile` | Рецепт сборки образа приложения |
| `.dockerignore` | Что не должно попасть в образ: Git, секреты, кэши |
| `docker-compose.yml` | БД, инициализация, приложение, сеть и volume |
| `.env.example` | Документированный пример параметров запуска |
| `backend/tests/` | API-тесты с PostgreSQL и независимые проверки старта |
| `.github/workflows/ci.yml` | Автоматический запуск тестов в GitHub Actions |
| `Отчёт.md` | Соответствие приложения 12 факторам |

`Dockerfile` и Compose решают разные задачи. Первый создаёт образ — шаблон файловой системы и запуска. Второй создаёт контейнеры из образов и связывает их. Volume `postgres_data` хранит данные вне жизненного цикла контейнера БД. `docker compose down` обычно сохраняет его; `down -v` удаляет данные.

## 3. Что именно было неправильно с конфигурацией

В старой версии `PORT` использовался только в `app.run(...)`. Но контейнер не выполнял `python app.py`: он запускал Gunicorn, а условие `if __name__ == '__main__'` при импорте не выполняется. Поэтому Gunicorn всегда слушал 8000, независимо от окружения.

Теперь `Dockerfile` запускает Gunicorn с `backend/gunicorn.conf.py`. Этот конфиг читает `PORT` в момент старта. `EXPOSE 8000` в Dockerfile — метаданные о стандартном порте, а не настройка прослушивания и не публикация порта.

В Compose есть два порта: `HOST_PORT` слева и `PORT` справа. Например, `HOST_PORT=8080 PORT=9000` означает: браузер открывает localhost:8080, Docker перенаправляет запрос в контейнер на 9000, Gunicorn действительно слушает 9000.

Параметры PostgreSQL тоже вынесены в окружение. `POSTGRES_*` — интерфейс официального образа PostgreSQL, `PG*` — интерфейс клиентской библиотеки libpq/psycopg. Это две стороны одних настроек. Отдельные переменные избавляют от ручного URL-кодирования пароля при сборке строки подключения. `DATABASE_URL` остаётся доступен как явная альтернатива вне Compose.

`.env` — локальный файл для подстановок Compose. Сам по себе Flask его не читает. При запуске Python напрямую нужно экспортировать переменные в shell. Смена `POSTGRES_PASSWORD` в `.env` не меняет пароль в уже инициализированном volume: для существующей БД пароль меняют SQL-командой. Нельзя удалять volume с ценными данными ради такой смены.

## 4. Почему init_db при импорте — не административный процесс

Gunicorn импортирует WSGI-приложение в рабочих процессах. Если импорт создаёт таблицы, запуск HTTP-сервера неявно меняет схему. При нескольких workers или репликах один и тот же DDL выполняется несколько раз. Веб-процессу оказывается нужна привилегия изменения схемы, а ошибку миграции трудно отделить от ошибки старта HTTP.

Теперь схема создаётся явно:

```bash
python -m backend.manage init-db
```

В Compose порядок задан зависимостями: БД становится healthy → `init-db` выполняется и завершается с кодом 0 → запускается `web`. Это самостоятельный процесс с тем же образом, кодом, зависимостями и параметрами окружения. При ошибке инициализации веб-сервис не стартует.

`CREATE TABLE IF NOT EXISTS` допускает повторный запуск, но не добавит новый столбец в старую таблицу. Для развития схемы нужны настоящие миграции, например Alembic. Это отдельное будущее улучшение.

## 5. Почему проверка HTML не защищает API

`maxlength="160"` ограничивает только ввод в конкретном браузерном поле. Любой клиент может выполнить прямой HTTP-запрос. Ограничение `VARCHAR(160)` защищает целостность БД, но если оставить только его, исключение попадёт в общий обработчик `psycopg.Error` и клиент увидит ошибочное сообщение о соединении и 503.

Теперь после `strip()` проверяется длина в Python — и при POST, и при PUT. Название из 160 символов допускается, из 161 возвращает 400: «Название задачи должно быть не длиннее 160 символов». Проверяется нормализованное значение, которое реально сохранится. Для Unicode считаются кодовые точки; это не всегда число визуальных символов сложного emoji.

Тесты проверяют обе границы, оба метода и сохранность старого названия после неудачного обновления. Ещё один тест подменяет соединение функцией, которая падает при вызове: так доказывается, что некорректное название отвергается раньше обращения к БД.

## 6. Как запустить и проверить самому

```bash
cp .env.example .env
docker compose up --build
# В другом терминале:
curl http://localhost:8000/health
docker compose ps -a
docker compose logs init-db
docker compose run --rm web python -m pytest -q
```

Тесты очищают таблицу `tasks`: запускай их только на учебной/тестовой БД, не на базе с нужными задачами. Для проверки другого порта измени `PORT=9000`, сохрани `HOST_PORT=8000` и пересоздай сервисы через `docker compose up --build`.

Запуск тестов без БД:

```bash
python -m pytest backend/tests/test_startup.py -q
```

Полный набор требует PostgreSQL. В CI он уже запускается отдельным service container. Ошибка отчёта была именно в утверждении, что тесты ещё предстоит добавить.

## 7. Что означают 12 факторов простыми словами

Одна кодовая база; явные зависимости; конфигурация вне кода; подключаемые внешние сервисы; разделённые сборка/релиз/запуск; процессы без пользовательского состояния в памяти; свой HTTP-порт; масштабирование процессами; безопасные перезапуски; близкие окружения; логи как поток; отдельные административные команды. Это принципы эксплуатации приложения, а не список библиотек, которые достаточно установить. В отчёте важно описывать реально работающий механизм и честно называть ограничения.

## 8. Как смотреть изменения

Для каждой домашки используется одна ветка: `hw_1`–`hw_6`. Все доработки и исправления коммитятся и отправляются прямо в ветку соответствующей домашки. В `hw_1` уже включены исправления замечаний. Домашки образуют последовательную цепочку; для просмотра изменений сравнивайте текущую ветку с предыдущей. Новые коммиты в предыдущей домашке не появляются в следующих автоматически: при необходимости их переносят отдельно.

```bash
git diff master...hw_1
git log --oneline master..hw_1
```

Для просмотра только исправлений замечаний сравнивайте с исходным коммитом: `git diff dddc941...hw_1`. Следующая домашка просматривается через `git diff hw_1...hw_2`.
