# ДЗ‑3: зачем логам структура и отдельное хранилище

## Лог — это событие

«В 14:00 запрос POST завершился кодом 400 за 3 мс» — лог. «За минуту было 12 ошибок» — уже агрегат. Логи полезны, когда нужно понять конкретный случай: что произошло, где и с каким запросом. Метрики, которые появятся дальше, удобнее для долгих графиков и сигнализации.

Строку `request failed` человеку прочитать легко, но машине неясны сервис, время, уровень и причина. JSON даёт явные ключи. Каждая запись — одна физическая строка; перевод строки внутри сообщения JSON-кодируется как `\n`, поэтому одно событие не превращается в несколько строк контейнерного лога.

`backend/logging_config.py` задаёт формат для Python и Gunicorn. В `before_request` сохраняются часы и уникальный ID. В `after_request` вычисляется длительность и пишется результат. Для длительности используется монотонный `perf_counter`, а для календарной даты — UTC: перевод системных часов не должен делать длительность отрицательной.

## Почему stdout

Приложение не должно решать, в какой файл складывать логи, когда его ротировать и как отправлять в удалённое хранилище. Оно выдаёт поток stdout. Контейнерный runtime записывает его на узле; сборщик занимается доставкой. Это развитие фактора Logs из ДЗ‑1.

Фактическая строка файла на Kubernetes-узле обычно имеет CRI-обёртку: время runtime, stdout/stderr, признак целой/частичной строки и содержимое. Нельзя просто ожидать чистый JSON от начала строки `/var/log/pods/...`: сначала нужно разобрать внешний формат. Это делает источник Vector `kubernetes_logs`.

## Почему Vector запускается на каждом узле

DaemonSet поддерживает по экземпляру сборщика на каждом подходящем узле. В однодовом minikube это один Vector. В большом кластере каждый читает локальные файлы своего узла, а все отправляют в общее хранилище. Если использовать обычный Deployment с одной репликой, сборщик может оказаться только на одном узле и не видеть логи остальных.

RBAC нужен для чтения метаданных: namespace, pod, container, labels. hostPath нужен для файлов. Это два разных доступа. Mount `/var/log` сделан read-only, а отдельный state-каталог — writable для offsets и буфера. Запуск под root выбран из-за прав файлов runtime в учебном кластере; это не означает, что приложению нужен root.

## Путь одного события

Flask сериализует JSON → runtime записывает CRI-строку → Vector читает её и получает JSON в поле message → VRL разбирает JSON и объединяет его с Kubernetes-метаданными → HTTP sink отправляет набор JSON-строк → VictoriaLogs индексирует поля и сохраняет событие → LogsQL выбирает нужные записи.

Настройки `_time_field` и `_msg_field` определяют, какое поле считать временем события и основным сообщением. `_stream_fields` задаёт устойчивую группировку потоков; request_id туда не включён, иначе почти каждый запрос становился бы отдельным потоком.

## Как читать LogsQL

Слева до `|` находятся фильтры: время, сервис, уровень. После `|` — операции над выбранными событиями. `sort` сортирует, `limit` ограничивает, `stats by` группирует, `top` показывает самые частые значения. Между фильтрами по умолчанию действует AND.

`count()` считает записи. Чтобы считать только HTTP-запросы, добавь `event:="http_request"`. Если учитывать все события, туда попадут старты процессов и дополнительные ошибки. В будущем то же правило понадобится для SLI: прежде чем писать формулу, нужно определить, что именно является одной операцией.

## Как искать проблему доставки

1. Нет строки в `kubectl logs` приложения — проверять логирование приложения.
2. Есть строка, но Vector пишет parse error — проверить JSON и CRI transform.
3. Vector пишет connection refused — Service, DNS, порт и готовность VictoriaLogs.
4. Ошибка forbidden — ServiceAccount и ClusterRoleBinding.
5. Приём работает, но vmui пустой — namespace/label selectors, фильтр сервиса и диапазон времени.
6. Логи приходят с запозданием — проверить буфер, ретраи и ресурсы получателя.

Наличие работающего пода VictoriaLogs ещё не доказывает доставку. Полная проверка — выполнить действие в UI и найти именно это свежее событие в vmui с корректными полями.

## Что сравнивать

`git diff hw_2...hw_3` показывает JSON-логирование, Vector, VictoriaLogs и запросы. CRUD остаётся прежним. Пользователь получает дополнительно `X-Request-ID`, который можно назвать при разборе ошибки.
