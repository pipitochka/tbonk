# ДЗ‑3. Структурированные логи и VictoriaLogs

## Стек и доставка

Flask и Gunicorn → JSON в stdout → файл CRI на узле Kubernetes → Vector DaemonSet → HTTP JSON Lines → VictoriaLogs single-node с PVC → vmui.

VictoriaLogs слушает 9428 внутри namespace `monitoring`; диск — 2 GiB, срок хранения — 7 дней. Vector читает только поды с `app=tbonk` в namespace `tbonk`, добавляет метаданные Kubernetes, разбирает JSON из `.message`. Для отслеживания смещений и буфера до 256 MiB используется каталог узла. После временной недоступности получателя Vector повторяет доставку. Это не гарантия exactly-once: при сбоях возможны потери или повторы, особенно при удалении узла/ротации логов и заполненном буфере.

Выбран DaemonSet, чтобы сбор не зависел от числа веб-реплик и не требовал встраивать клиент хранилища логов в приложение. Контейнеру Vector нужен доступ только на чтение к `/var/log` и RBAC get/list/watch для метаданных; доступ к API не позволяет ему изменять приложение. Источник `kubernetes_logs` понимает CRI-обёртку, после чего отдельный transform разбирает вложенный JSON приложения.

## Поля события

Обязательные: `timestamp` (UTC ISO 8601), `level`, `message`, `service.name`. Событие HTTP также содержит `event=http_request`, `request_id`, `http.method`, `http.route`, `http.status_code`, `duration_ms`. Идентификатор возвращается клиенту в `X-Request-ID`.

Маршрут содержит шаблон `/api/tasks/<int:task_id>`, а не произвольный URL с данными пользователя. Тело запроса, пароль БД и query string не пишутся. 2xx/3xx → info, 4xx → warning, 5xx → error. Технические проверки `/live` и `/health` исключены из access-событий. Логи жизненного цикла Gunicorn тоже JSON; второй дублирующий access-log Gunicorn отключён.

При приёме VictoriaLogs превращает `timestamp` в `_time`, а `message` в `_msg`. Остальные поля остаются доступны для фильтров. Поэтому в vmui время и текст будут показаны под служебными именами, хотя stdout содержит исходную схему.

## Запуск

Собрать `tbonk-tasks:hw3`, загрузить в профиль `tbonk-homework` способом из ДЗ‑2. Для Podman при экспорте tar сначала присвоить образу имя `docker.io/library/tbonk-tasks:hw3`, соответствующее разрешению имени в манифесте.

```bash
bash scripts/deploy-app.sh
bash scripts/deploy-logs.sh
kubectl --context tbonk-homework -n monitoring get pods,svc,pvc
kubectl --context tbonk-homework -n tbonk logs deployment/tbonk --tail=10
kubectl --context tbonk-homework -n monitoring logs daemonset/vector --tail=30
kubectl --context tbonk-homework -n monitoring port-forward svc/victorialogs 9428:9428
```

Открыть http://localhost:9428/select/vmui/. В VictoriaLogs интерфейс находится под `/select/vmui/`, в отличие от `/vmui/` у VictoriaMetrics. В отдельном терминале пробросить приложение на 8000, создать и прочитать несколько задач. Чтобы гарантированно получить warning, отправить пустое название:

```bash
curl -i -H 'Content-Type: application/json' -d '{"title":""}' http://localhost:8000/api/tasks
```

## Четыре запроса

Запросы также сохранены по одной строке в `queries.logsql`. В vmui выбрать временной диапазон, включающий запуск; собственный `_time:15m` ограничивает последние 15 минут.

### 1. Сырые события

```logsql
_time:15m service.name:="tbonk-tasks" | sort by (_time) desc | limit 100
```

Последние 100 событий приложения. Проверяем поля, timestamp, pod и сообщения. Это исходная диагностика конкретных запросов, а не агрегированная метрика.

### 2. Фильтр по уровню

```logsql
_time:15m service.name:="tbonk-tasks" level:="warning"
```

Неуспешные клиентские запросы, например пустое или слишком длинное название. Выбран warning, чтобы демонстрация не требовала ломать БД. Для серверных ошибок используется `level:="error"`. Пустой результат может означать отсутствие событий данного уровня, а не поломку сбора.

### 3. Группировка stats

```logsql
_time:15m service.name:="tbonk-tasks" | stats by (service.name, level) count() as events
```

Число событий по сервису и уровню за окно. Это количество записей лога: одна ошибка БД может породить и событие `database_error`, и access-событие, поэтому результат нельзя автоматически считать количеством HTTP-запросов.

### 4. Агрегация top

```logsql
_time:15m service.name:="tbonk-tasks" event:="http_request" | top 5 by (http.route)
```

Пять наиболее часто встречавшихся маршрутов. Ограничение `event=http_request` исключает сообщения старта Gunicorn. Нормализованные маршруты не разбиваются на отдельную строку для каждого task_id.

## Что показать на экране

Для каждого запроса выполнить поиск в vmui и сохранить реальный скриншот с текстом запроса, диапазоном времени и результатом. Для второго запроса сначала создать 400. Скриншоты нельзя заменить придуманными картинками. Фактические проверки и доступные подтверждения перечисляются в общем `docs/Проверка.md`, когда он добавлен; этот текст сам по себе не утверждает, что скриншоты уже сделаны.

Бонус Grafana/vmalert по логам здесь не реализован: базовый сценарий использует vmui; алерты на метрики появляются в ДЗ‑6.
